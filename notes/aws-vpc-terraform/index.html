What a small AWS VPC lab teaches about cloud engineering

A useful infrastructure portfolio should explain the design, show the source, and make its verification limits clear.

Jamie Christian II · November 23, 2026

Scope: This independent learning lab defines AWS networking resources in Terraform. The configuration was validated locally; AWS infrastructure was not deployed. Application and database workloads are conceptual.

1. Separate reachability from access

A virtual private cloud defines the network boundary. The public subnet has a route toward an internet gateway and automatic public IPv4 assignment for eligible resources. The private subnet has neither automatic public IPv4 assignment nor a default internet route in this lab.

2. Use security group references

The application security group permits HTTPS ingress on TCP 443 from IPv4 addresses. PostgreSQL ingress on TCP 5432 references the application security group instead of allowing arbitrary internet addresses. The app-to-database egress rule also uses a security group reference.

This illustrates a narrower access path, not a complete production security design. A live deployment would require reviewing actual workloads, identity controls, logging, availability and cost.

3. Validate without deploying

These commands check configuration format, initialize providers without a backend, and validate Terraform configuration. They do not create AWS resources.

terraform fmt -check -recursive
terraform init -backend=false -lockfile=readonly -input=false
terraform validate -no-color

The repository also contains a GitHub Actions validation workflow. Review the current run status separately: a workflow definition is not proof that it passed.

4. Document what remains unverified

The lab does not establish live connectivity, production availability, load balancing, database deployment, or operational monitoring. Those are separate design and testing milestones. Clear limitations make a portfolio easier to trust and discuss in an interview.
